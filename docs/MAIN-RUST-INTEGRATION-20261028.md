# Intégration Rust dans main

La fusion conserve les deux historiques. Le moteur Go supprimé par la migration n’est pas réintroduit. Les contrôles SQLite sont ceux du moteur Rust, persistés et accessibles par les réglages natifs ; les guides et recettes Go sont historiques. Les ajouts de formation/Docker de main sont conservés. Les préimages historiques ne sont pas fusionnées textuellement : la variante migration reste à son chemin, la variante main reste dans son commit parent.

Le vérificateur de méthodes appelle le test Rust agent_workflow, exige les neuf contrats nommés et refuse une collecte vide. Les profils CI sans debug/incrémental correspondent à la construction locale qualifiée, sans changer les politiques métier ni retirer de contrôle. Les changements non committés du poste sont préservés. CI checks/install restent nécessaires avant fusion ; aucune acceptation indépendante ou activation d’identité réelle ne découle de ce document.

La première CI a révélé deux fixtures de tests omises et une recette supposant le parent du répertoire de preuve déjà présent. Les fixtures synthétiques référencées sont publiées ; les deux recettes créent les parents manquants et refusent toujours un résultat existant. La revue des includes littéraux porte désormais sur toutes les sources Rust publiées, et non seulement les fichiers modifiés. Aucun test de bibliothèque ne s’était exécuté lors de cet échec de compilation.

La seconde CI a exécuté 632 tests moteur avec succès et révélé six échecs : quatre assertions historiques de version de schéma et deux traversées ne suivant pas le wrapper Linux des erreurs de fichier. Les tests préservent désormais les groupes de réglages plus récents ; la classification utilise le graphe typé commun, refuse toujours les erreurs inconnues et de nettoyage, sans accès supplémentaire. Les erreurs Docker sont conservées et exposées dans la CI, plutôt que réduites à un code sans cause.

Le contexte Docker autorise explicitement les cinq JSON de configuration embarqués (attente fournisseur, logs, activité, graphes, requêtes web). Le contrôle de distribution recense leurs inclusions littérales et refuse un défaut de publication ou de liste Docker ; il ne remplace pas la construction réelle. Un chemin de module erroné dans le nouveau test a été conservé comme échec de compilation puis corrigé.

Les deux dernières fixtures historiques sont désormais reconstruites via introduced_schema_version du catalogue : versions 40 puis 39 pour la disparition du réglage de rapport, version 40 puis 41 pour le groupe de lecture de préparation. Les dépendances de groupes récents ne sont plus mélangées à une ancienne configuration ; les validations du moteur restent strictes. Le générateur est exclusivement compilé en test.

Les 639 tests moteur passent ; trois tests de liaison identité nécessitent une fixture réellement placée dans un autre espace de noms. Le runner ubuntu-latest a refusé uid_map (EPERM). Lors de l’essai précédent, le job checks sélectionnait Ubuntu 22.04 et contrôle ce prérequis avant compilation, sans sudo, changement AppArmor/sysctl ni test ignoré ; install reste sur ubuntu-latest. Cela ne qualifie pas le déploiement dans tous les environnements Linux. Le propriétaire CI devra revalider un successeur compatible avant le retrait de cette image. Sources : [restrictions Ubuntu](https://documentation.ubuntu.com/security/security-features/security-features-tables/), [image GitHub Ubuntu 22.04](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2204-Readme.md).

Le candidat intègre également les deux commits publiés pendant cette intégration (2bec348fc, 9ebb8e393) : liaison Git privée/flux PAEA et fichiers de projet restants. Les trois conflits README/notes de version conservent le nouveau contenu et la déclaration Rust de main. Le vérificateur inclut la skill pricing-discovery désormais publiée. Python 3.13 est sélectionné explicitement pour les outils de build utilisant hashlib.file_digest, absent du Python 3.10 par défaut d’Ubuntu 22.04. Aucun fichier privé de runtime ni Go exécutable réintroduit.

Le propriétaire a autorisé explicitement le réglage des namespaces sur la seule VM GitHub CI jetable. Le job checks utilise Ubuntu24.04 (noyau récent), conserve kernel.apparmor_restrict_unprivileged_userns puis le règle temporairement à0, exige la fixture unshare et restaure la valeur initiale dans une étape always. Aucun réglage du poste local ni test supprimé. Python3.13 reste explicite ; le job install conserve son environnement séparé. L’ancien essai Ubuntu22.04 échouait sur les ioctls pidfd malgré unshare disponible ; ce runner n’est plus celui du contrat courant.
