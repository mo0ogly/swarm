## 1. Parcours (journeys)

Trois parcours, un par role defini en F1 :

- **J-prospect** (decouverte, catalogue) : arrivee page publique -> graphe/preuves
  exemple -> cinq fondations/six etapes -> catalogue -> choix modele -> sortie vers
  creation de compte ou depart sans compte.
- **J-client** (sessions, ressources, demarrage) : connexion -> espace personnel ->
  ressources autorisees -> guide installation/fournisseurs/projet -> preparation
  Swarm local -> deconnexion/revocation.
- **J-admin** (administration, revocation) : connexion admin -> recherche compte ->
  consultation droits/journal -> attribution/retrait de droit -> revocation verifiee
  serveur -> journal d'audit global.

Detail pas a pas et conditions de sortie dans `F2.spec.json` champ `journeys`.

## 2. Stories (sept, avec id/criteres/dependances/etats)

| Story | Journey | Depend de | Criteres cles |
| --- | --- | --- | --- |
| decouverte | J-prospect | — | Enonce moteur/agents <2 ecrans, graphe exemple sans compte |
| catalogue | J-prospect | decouverte | Liste modeles, comparaison, choix sans engagement moteur |
| sessions | J-client | — | Session avec expiration, deconnexion/echec sans fuite d'info |
| ressources | J-client | sessions | Lecture limitee, refus serveur hors-compte |
| demarrage | J-client | sessions, ressources | Guide sequentiel jusqu'a preparation reelle Swarm local |
| administration | J-admin | sessions | Recherche compte, droits traces, role verifie serveur |
| revocation | J-admin | administration, sessions | Refus serveur immediat et verifiable apres revocation |

Chaque story porte dans `F2.spec.json` : `id`, `journey`, `criteria` (liste de
criteres observables), `depends_on` (autres stories), `states` (quatre etats
chargement/vide/erreur/succes, texte concret par story, pas un placeholder
generique). Couverture complete des sept stories du plan (decouverte, catalogue,
sessions, ressources, demarrage, administration, revocation) : confirmee.

## 3. Dependances (dependencies)

Sept relations explicites avec raison fonctionnelle (champ `dependencies`) :
catalogue->decouverte, ressources->sessions, demarrage->ressources,
demarrage->sessions, administration->sessions, revocation->administration,
revocation->sessions. Aucune dependance circulaire : l'ordre topologique est
decouverte -> catalogue -> sessions -> {ressources, administration} ->
{demarrage, revocation}.

## 4. Etats d'erreur obligatoires (error_states)

Huit cas, dont les cinq cas obligatoires du brief explicitement couverts :

- **E1** deux comptes distincts (A lit une ressource de B) -> refus serveur sans
  fuite de metadonnee.
- **E2** URL directe vers ressource privee -> meme controle que la liste, pas de
  contournement.
- **E3** identifiant de ressource devine/enumere -> refus uniforme (anti
  enumeration).
- **E4** compte anonyme sur endpoint protege -> 401 explicite, aucune donnee
  partielle.
- **E5** session revoquee qui rejoue un appel valide -> refus serveur immediat,
  independant du cache client.
- **E6** client tentant un ecran administrateur -> 403, role insuffisant trace.
- **E7** echec reseau/fournisseur pendant le guide de demarrage -> message
  specifique, progression preservee.
- **E8** authentification echouee -> message generique identique (compte
  inexistant vs mot de passe faux non distingues).

Chaque cas reference les stories concernees dans `F2.spec.json`. Ces huit cas
couvrent integralement les cinq cas obligatoires cites par le plan (deux comptes,
URL directe, identifiant devine, compte anonyme, session revoquee) et en ajoutent
trois complementaires (role insuffisant, echec guide, echec authentification)
necessaires pour couvrir les sept stories sans trou.
