# F1 — Definir les besoins du portail client Swarm

Tache plan-a77d9f4799-F1, role worker. Perimetre : portail client Swarm uniquement,
fichiers docs/portal-client-swarm. Aucun code moteur, aucune publication. Ce rapport
et docs/portal-client-swarm/F1.spec.json forment le candidat de cette tache ; aucune
fondation anterieure acceptee n'existait dans ce depot gere (dossier absent avant
cette tentative), donc F1 part du brief adopte et des sept stories du plan.

## 1. Utilisateurs (users)

Trois roles couvrent les sept stories :

- **Prospect anonyme** — stories decouverte, catalogue. Objectif : comprendre Swarm
  (moteur deterministe separe des agents IA, meilleure coordination des
  responsabilites, visibilite du travail, preuves, reprise), voir le graphe et les
  preuves, comprendre les cinq fondations et les six etapes par fonctionnalite,
  choisir un modele. Aucun compte requis, acces lecture seule uniquement.
- **Client connecte** — stories sessions, ressources, demarrage. Objectif : se
  connecter, acceder a son espace personnel, consulter les ressources qui lui sont
  autorisees, suivre le guide d'installation/fournisseurs/projet, preparer son
  lancement dans Swarm local ou les decisions et autorisations sont appliquees par
  le moteur. Contrainte forte : isolation stricte de compte.
- **Administrateur plateforme** — stories administration, revocation. Objectif :
  selectionner un compte, attribuer ou retirer des droits, verifier que le refus
  serveur est bien effectif apres une revocation, consulter le journal d'audit.

Detail structure dans `F1.spec.json` champ `users`.

## 2. Besoins (needs)

Un besoin par story, plus un besoin transversal :

| ID | Story | Besoin | Priorite |
| --- | --- | --- | --- |
| N1 | decouverte | Presentation publique comprehensible de Swarm, FR/EN, mobile/bureau | must |
| N2 | catalogue | Liste des modeles avec cinq fondations / six etapes, comparaison et choix | must |
| N3 | sessions | Authentification, session avec expiration, deconnexion et revocation immediate | must |
| N4 | ressources | Acces lecture limite aux ressources autorisees, refus de tout acces hors compte | must |
| N5 | demarrage | Guide installation / fournisseurs / projet jusqu'a preparation Swarm local | must |
| N6 | administration | Recherche de compte, modification de droits, journal horodate | must |
| N7 | revocation | Refus serveur effectif et immediat apres revocation, verifiable independamment de l'UI | must |
| N8 | transversal | FR/EN, mobile/bureau, clavier, quatre etats (chargement/vide/erreur/succes) sur chaque ecran | must |

Detail dans `F1.spec.json` champ `needs`.

## 3. Perimetre (scope)

Inclus dans ce portail :

1. Pages publiques : presentation Swarm, graphe/preuves, catalogue de modeles,
   explication des cinq fondations et six etapes.
2. Compte client : connexion, espace personnel, ressources autorisees, guide de
   demarrage (installation, fournisseurs, projet), preparation locale.
3. Administration : selection de compte, attribution/retrait de droits, journal
   d'audit, revocation de session ou d'acces.
4. Contrats API portant isolation de compte, controle d'acces fichiers, expiration
   de session, revocation effective.
5. Design system FR/EN mobile/bureau avec les quatre etats sur chaque ecran listé
   ci-dessus.

## 4. Exclusions

- Aucune implementation du moteur Swarm lui-meme, de ses missions existantes, bases
  privees, budgets ou preuves historiques : le portail reste client de ces contrats.
- Aucun push, publication externe, paiement reel ou connexion a un service distant
  depuis cette tache.
- Aucun code moteur ni modification de `.swarm/state.db`.
- Pile technique definitive, hebergement et offre commerciale non tranches ici :
  decisions explicites attendues en F4 (architecture), apres comparaison d'au moins
  deux options.
- Les six etapes de realisation par story (recherche, conception, planification,
  realisation, validation, livraison) restent non planifiees jusqu'a leur examen ;
  F1 ne produit pas ce plan de realisation.
- Aucune authentification tierce reelle (OAuth externe, SSO) specifiee au-dela
  d'une decision ouverte (voir D1).

## 5. Criteres de succes (success)

| ID | Critere | Mesure |
| --- | --- | --- |
| S1 | Prospect comprend moteur vs agents en <2 ecrans, voit un exemple de graphe/preuves sans compte | Revue/test utilisateur |
| S2 | Isolation stricte : jamais d'acces a une ressource d'un autre compte (URL directe, identifiant devine, anonyme, session revoquee) | Cinq cas obligatoires testes -> refus serveur effectif |
| S3 | Revocation produit un refus serveur verifiable immediatement, pas seulement un changement d'affichage | Rejouer un appel API valide apres revocation -> refus explicite |
| S4 | Parcours client complet FR/EN, mobile/bureau, clavier | Parcours rejoue dans ces quatre configurations sans blocage |
| S5 | Quatre etats (chargement/vide/erreur/succes) presents sur chaque ecran du parcours | Inventaire d'ecrans verifie en revue des maquettes F5 |

## 6. Decisions ouvertes (open_decisions)

| ID | Question | Raison |
| --- | --- | --- |
| D1 | Authentification locale (mot de passe) ou delegation OAuth externe ? | Impacte F4 et le cout des sessions ; aucune connexion externe reelle n'est autorisee sans decision explicite de l'utilisateur |
| D2 | Droits administrateur binaires (actif/revoque) ou granulaires par ressource ? | Un role binaire suffit aux sept stories actuelles mais limite un partage selectif futur |
| D3 | Frontiere portail commercial / moteur Swarm local : donnees stockees par le portail vs relayees depuis une installation locale | A comparer en F4 avec au moins deux options argumentees avant toute decision d'architecture |
| D4 | Duree et politique d'expiration de session (fixe, glissante, ou revocation manuelle uniquement) | Affecte directement S2/S3 ; a fixer avant les contrats API de F3 |
| D5 | Journal d'audit visible au client concerne ou reserve a l'administrateur | Question de transparence vs confidentialite ; a trancher avant la conception d'ecran F5 |

Ces decisions sont motivees mais non tranchees ici : elles restent ouvertes pour
revue et decision explicite avant les fondations dependantes (F3 contrats API,
F4 architecture, F5 conception d'ecran).
