# F3 — Verifier la couverture

Fondation 3 du portail client Swarm. Depend de F2 (parcours/stories acceptee).
Perimetre strict : docs/portal-client-swarm uniquement, aucun code moteur,
aucune publication. Detail structure dans docs/portal-client-swarm/F3.spec.json.

## Objet

Produire la matrice complete story -> ecran -> API -> preuve pour les sept
stories de F2 (decouverte, catalogue, sessions, ressources, demarrage,
administration, revocation), sans omission, puis identifier les lacunes et
les decisions necessaires pour que cette matrice tienne (coverage, gaps,
decisions, evidence_plan dans le JSON).

## Methode

1. Lecture de F2.spec.json (sept stories, journeys, huit cas d'erreur E1-E8,
   dependances, decisions ouvertes heritees D1/D4/D5) et de F1.spec.json
   (D1, D2, D3, D4, D5 completes avec leur statut "ouverte").
2. Pour chaque story : ecrans necessaires, endpoints API candidats (methode,
   chemin, niveau d'authentification, but), et liste des preuves/tests qui
   demontrent chaque critere F2 (y compris les etats loading/empty/error/
   success et les cas d'erreur E1-E8 explicitement references).
3. Identification des lacunes ou la matrice depend d'une decision non
   tranchee (D1, D2, D5 heritees), plus deux lacunes propres a F3 (inscription
   compte, schema d'identifiant de ressource).
4. Trois decisions d'echafaudage prises dans le perimetre de cette tache pour
   que la matrice soit concrete (politique de session, politique de message
   d'erreur generique, schema d'identifiant opaque) — voir justification
   detaillee ci-dessous et dans le JSON.
5. Plan de preuves (evidence_plan) : tests a construire par story, non
   executes dans cette tache (aucun code moteur autorise ici).

## Couverture (resume ; detail complet dans le JSON)

| Story | Ecrans | Endpoints API | Cas d'erreur F2 references |
| --- | --- | --- | --- |
| decouverte | Page publique, section graphe exemple | GET /api/public/landing-content, GET /api/public/example-graph | aucun (parcours public, pas d'auth) |
| catalogue | Liste modeles, fiche modele, comparateur | GET /api/public/models, GET /api/public/models/{id} | aucun |
| sessions | Formulaire connexion | POST /api/auth/login, POST /api/auth/logout, GET /api/auth/session | E8 |
| ressources | Liste ressources, detail ressource | GET /api/me/resources, GET /api/me/resources/{id} | E1, E2, E3, E4, E5 |
| demarrage | Guide sequentiel, recapitulatif | GET /api/me/onboarding/state, POST .../steps/{id}/validate, POST .../complete | E7, E4 |
| administration | Recherche compte, fiche compte, journal global | GET /api/admin/accounts, GET /api/admin/accounts/{id}, PATCH .../rights, GET /api/admin/audit-log | E6 |
| revocation | Action revoquer, confirmation journal | POST .../sessions/revoke, POST .../rights/revoke | E5 |

Les sept stories de F2 sont couvertes sans omission. Les huit cas d'erreur
E1-E8 de F2 sont tous references au moins une fois dans la matrice (E1-E5 sur
ressources/sessions/revocation, E6 sur administration, E7 sur demarrage, E8 sur
sessions).

## Lacunes (gaps)

- **G1** — D1 (authentification locale vs OAuth) non tranchee : la matrice
  suppose un mot de passe local par defaut (coherent avec l'interdiction de
  connexion reelle a un service distant dans ce perimetre), a confirmer avant
  implementation.
- **G2** — D2 (granularite des droits admin) non tranchee : change le corps de
  PATCH /api/admin/accounts/{id}/rights (booleen vs liste de scopes), pas le
  contrat d'URL.
- **G3** — D5 (visibilite journal au client) non tranchee : si tranchee oui, un
  endpoint GET /api/me/audit-log manquera a la story ressources.
- **G4** — Aucun endpoint d'inscription (POST /api/auth/register) n'est dans la
  matrice ; a confirmer si l'auto-inscription est dans le perimetre produit.
- **G5** — Schema exact des identifiants opaques (UUID v4 ou autre) renvoye a
  F4 ; seule la direction (opaque, non sequentiel) est fixee ici.

Aucune de ces lacunes n'est bloquante pour cette fondation : elles sont
explicitement portees au dossier plutot que masquees par un choix implicite.

## Decisions prises dans ce perimetre

Trois decisions d'echafaudage, necessaires pour que la matrice API soit
concrete plutot que vague, sont enregistrees dans F3.spec.json (D-F3-1,
D-F3-2, D-F3-3) :

1. **Session server-side avec expiration courte fixe** (D-F3-1, repond a D4
   heritee) : un JWT stateless sans liste de revocation ne peut pas satisfaire
   le cas E5 (refus immediat apres revocation) sans verification d'une liste
   noire a chaque appel — ce qui revient de fait a un etat server-side. Autant
   assumer directement une session server-side. Reste soumise a confirmation
   explicite de l'utilisateur en F4 (choix technologique final), car c'est un
   choix d'architecture backend.
2. **Message d'erreur generique unique par categorie** (D-F3-2) pour
   authentification (E8) et acces ressource (E1-E3) : un message differencie
   reintroduirait une fuite d'information meme avec un bon code HTTP. Decision
   directement applicable, sans arbitrage utilisateur supplementaire.
3. **Identifiants opaques non sequentiels** (D-F3-3) pour toute ressource/
   compte reference dans une URL : un identifiant sequentiel rend l'enumeration
   triviale (E3) independamment des controles d'autorisation. Decision
   directement applicable ; schema de generation precis renvoye a F4 (gap G5).

Ces decisions ne tranchent pas D1/D2/D5 heritees de F1 : elles rendent
seulement la matrice F3 concrete sans presumer les choix d'architecture
backend complets reserves a F4.

## Plan de preuves (evidence_plan)

Pour chaque story, une liste de controles a construire en phase de
realisation (six etapes par fonctionnalite), avec priorite sur ressources et
revocation qui portent le plus de cas d'erreur critiques (E1-E5). Aucun de ces
controles n'est execute dans cette tache : perimetre interdit tout code moteur
ou test automatise reel ici. Detail complet par story dans
F3.spec.json.evidence_plan.

Le cas le plus critique identifie est **revocation / E5** : rejouer un jeton
precedemment valide apres revocation doit produire un refus serveur immediat,
jamais un "succes degrade" — F2 exclut explicitement ce cas et F3 le retient
comme priorite de test avant toute autre optimisation.

## Verifications locales effectuees dans cette tache

- Lecture complete de F2.spec.json et F1.spec.json (open_decisions,
  decisions_recorded) pour fonder la matrice sur les stories/decisions
  reellement acceptees, pas une reconstruction a memoire.
- Controle structurel Python (python3 -c, voir ci-dessous) sur F3.spec.json et
  F3.md : presence des quatre champs obligatoires (coverage, gaps, decisions,
  evidence_plan) non vides, et longueur du rapport Markdown >= 500 caracteres.
- Verification manuelle que les sept stories de F2 apparaissent toutes comme
  cle dans coverage, et que E1 a E8 apparaissent chacun au moins une fois dans
  un champ error_states_covered ou evidence du JSON.

Ces verifications locales couvrent la structure et la tracabilite declarative
(presence des champs, correspondance story/erreur). Elles ne demontrent pas la
pertinence semantique des contrats API proposes ni l'exactitude des decisions
D-F3-1 a D-F3-3 : cette pertinence est explicitement reservee a la revue
independante (cf. bilan de livraison et limites ci-dessous).

## Limites

- Contrats API candidats, pas une architecture backend definitive (F4) ni une
  implementation. Aucun code moteur produit dans cette tache.
- D-F3-1 (session server-side) reste soumise a confirmation utilisateur
  explicite en F4 ; D-F3-2 et D-F3-3 sont directement applicables mais restent
  des choix de cette fondation, pas des contraintes imposees par F1/F2.
- G1-G5 restent ouvertes et doivent etre tranchees ou confirmees avant F4
  (architecture) et F5 (ecrans), selon le champ severity de chacune dans le
  JSON.
- evidence_plan decrit des controles a construire, pas des resultats observes
  : aucun test reel execute dans le perimetre de cette tache.
- Pertinence semantique de la matrice (choix d'endpoints, exhaustivite reelle
  des preuves par rapport aux besoins utilisateur) verifiee par revue
  independante uniquement ; les controles locaux ne verifient que la
  structure.
